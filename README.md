art_rag.py

A local, offline-first RAG (Retrieval-Augmented Generation) application built for art history research — painting techniques, pictorial movements, artists, and artwork analysis. Everything runs on your own machine: no cloud API, no data leaving your computer.

It ingests documents and web sources into a searchable knowledge base, analyzes artwork images with vision models, and lets you chat with an art-history assistant that grounds its answers in your own library — citing sources instead of hallucinating.

Highlights
Fully local & offline — powered by Ollama or LM Studio (your choice), plus ChromaDB and SQLite. Nothing is sent to a third-party API.
One file, one GUI, one CLI — a single Python module (art_rag.py) with a CustomTkinter desktop interface and a full command-line mode for scripting/automation.
Two interchangeable LLM backends — switch between Ollama and LM Studio from the Settings tab, no code changes required.
Structured auto-tagging — every ingested chunk is automatically tagged with artistic movement, artist, period, technique, and keywords by an LLM.
Vision-based artwork analysis — feed it a photo of a painting and get a structured art-historical analysis (single image or batch folder).
Conversational research assistant — a chat tab that routes between plain conversation, RAG-grounded Q&A, and structured image-prompt generation, with persistent multi-session history.
Built-in web research — pull in Wikipedia, the Met Museum's Open Access collection, and general web search, review results, and selectively ingest them.
Features
📄 Document ingestion (Documents tab / CLI ingest)
Ingest single files or entire folders recursively (PDF, TXT, MD).
Automatic semantic chunking, embedding, and storage in ChromaDB + SQLite.
LLM-based auto-tagging (movement, artist, period, technique, keywords) at two granularities:
document (fast — one LLM call per file, samples the text)
chunk (fine-grained — one LLM call per chunk)
Manual metadata override (force artist/movement/period/technique) when you know better than the model.
Re-ingestion protection: files already processed are skipped unless --force is used.
Progress tracking with ETA, per-chunk logging, and graceful resume after interruption.
🖼️ Artwork Analysis (Artwork Analysis tab / CLI ingest --image)

Organized into two clear sub-workflows:

Single Image — analyze one artwork at a time with a numbered step-by-step flow: load image → (optional) auto-fill from Met Museum → vision analysis → review → ingest into the knowledge base.
Batch Folder — analyze a whole folder of artwork images in one pass, with:
auto-ingest (straight into the database) or manual review queue before ingestion
optional auto-rename of files based on the detected artist/title
Vision analysis is generated by a local vision-capable LLM (fully offline — no external API calls), producing a structured art-historical write-up (composition, technique, palette, influences, etc.).
You can also supply your own hand-written analysis instead of generating one.
💬 Chat (Chat tab / CLI chat)
Multi-turn conversational interface with an intelligent router: each message is automatically classified as small talk, an art-history question (triggers RAG retrieval), or an image-prompt request.
RAG-grounded answers cite the specific documents/chunks they draw from.
Structured image-prompt generation: describe what you want and get back a strict 10-key JSON prompt (SUBJECT, POSE, ENVIRONMENT, STYLE, COLOUR PALETTE, LIGHT, MATERIAL, ATMOSPHERE, CAMERA, RENDER) — ready to feed into ComfyUI, Midjourney-style tools, or any structured image-generation pipeline.
Persistent conversation history (SQLite-backed), with automatic LLM-generated conversation titles.
Token-by-token streaming responses.
Adjustable context: how many RAG excerpts (top-k) and how much chat history are sent to the model.
🔎 Web Search (Web Search tab)

Search and selectively ingest external sources without leaving the app:

Wikipedia (official MediaWiki API, free, no key, configurable language) — reliable coverage of movements, artists, and techniques.
The Met Museum (Open Access API, free, no key) — structured museum-quality artwork metadata, converted into RAG-ready text, with thumbnail previews.
General web search (via ddgs / DuckDuckGo, fully local, no key) — for anything not covered by the above, in French and/or English.
Manual review before ingestion — nothing goes into your knowledge base without your say-so.
🔍 Question answering (CLI query)
Ask a question directly from the terminal and get a RAG-grounded answer with cited sources.
Filter by artistic movement, artist, or artwork.
Restrict search to artwork analyses only (excluding general documents).
Streamed or full-response output; optional display of the raw retrieved excerpts.
⚙️ Settings tab

Everything is configurable from the GUI (backed by art_rag_config.json, no need to edit code):

Backend — choose Ollama or LM Studio, and the LM Studio server URL.
Ollama — server URL, model names (embedding / reference / vision / answer / auto-tagging), VRAM keep-alive duration. (Same model-name fields double as the LM Studio model identifiers when that backend is active.)
Performance — context size, max response length, timeouts, embedding/LLM concurrency, batch size, top-k, chat history window.
Knowledge base — database paths, collection name, auto-tag granularity, document sampling size.
Web Search — Wikipedia language.
A built-in "list available models" button shows what's actually detected on the active backend, so you never have to guess a model identifier.
Local LLM backends

art_rag.py talks to your LLM through a single abstraction layer (llm_chat / llm_embed / llm_list_models), so you can freely choose between:

	Ollama (default)	LM Studio
API style	Native (/api/chat, /api/embeddings)	OpenAI-compatible (/v1/chat/completions, /v1/embeddings)
Setup	ollama serve running locally	Local Server started from LM Studio's Developer tab
VRAM management	Per-request keep_alive	Server-side JIT loading / idle TTL

Switching backends is a one-click change in Settings — the rest of the pipeline (chunking, tagging, embeddings, storage, chat) behaves identically either way.

IMPORTANT: ALWAYS SAVE IN THE SETTINGS WHEN YOU CHANGE A VALUE; OTHERWISE, THE CHANGES WON'T TAKE EFFECT
